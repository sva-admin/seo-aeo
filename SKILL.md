# /seo-aeo: Comprehensive SEO + AEO Build

A 9-phase, approval-gated workflow that ships every modern SEO + AEO best practice for a Next.js static-export site: per-page metadata, JSON-LD entity graph, llms.txt for AI engines, dynamic OG images, tuned sitemap, AI-crawler allowlist, and an operational runbook.

Born from a real production build (a bilingual, multi-location Next.js site shipped in 2026). Every pattern in this skill was verified live on Google, Vercel, and the AI-engine unfurl path. Pitfalls section captures things you'll hit but won't see coming.

## Usage

```
/seo-aeo                          # full 9-phase guided build, approval gates between phases
/seo-aeo --auto                   # best-effort with minimal approval gates (confident defaults)
/seo-aeo --phase <N>              # run only Phase N (1-9)
/seo-aeo --phases <N>-<M>         # range of phases
/seo-aeo --audit                  # read-only: report current state without making changes
/seo-aeo --help                   # print this usage block
```

## What this skill does

**SEO** = Search Engine Optimization. Targets Google, Bing, DuckDuckGo. Hub of techniques: metadata, structured data (JSON-LD), sitemaps, canonical URLs, hreflang, image alt text.

**AEO** = AI Engine Optimization. Targets ChatGPT, Claude, Perplexity, Gemini, Copilot. Newer practice: llms.txt files, robots.txt allowlists for AI crawlers (GPTBot, ClaudeBot, etc.), explicit content that AI engines can summarize.

The two stacks have ~70% overlap but distinct artifacts. This skill ships both.

**Final shape of the site after this skill:**

```
public/
  llms.txt                          # 500-700 words, AI-engine quick reference
  llms-full.txt                     # 2000-4000 words, comprehensive knowledge document
  google-site-verification.html     # placeholder for GSC HTML verification
  (robots.txt + sitemap.xml generated by next-sitemap at build time)

src/app/
  layout.tsx                        # Organization + WebSite JSON-LD site-wide
  page.tsx + */page.tsx             # per-page metadata + page-specific JSON-LD
  opengraph-image.tsx               # dynamic 1200×630 brand-aware PNG

next-sitemap.config.js              # AI crawler allowlist + per-route priority/changefreq
vercel.json                         # legacy redirects + Content-Type for OG image
deployment-runbook.md               # operational reference for site admin
```

## When to invoke

- User says "make this site discoverable", "SEO pass", "AEO pass", "ship for search", "optimize for ChatGPT/Claude search"
- A Next.js site is being launched and needs full search-engine and AI-engine readiness
- Migrating from a WordPress/legacy site that had SEO and you need to match or improve
- A founder asks how to get their site to show up in ChatGPT or Claude

Skip if:
- The site is server-rendered with dynamic content (most of this assumes `output: 'export'`; adapt the rest)
- The site is e-commerce with thousands of product pages (different shape, needs Product schema, Offer schema, dynamic sitemaps)
- The user only needs ONE artifact (e.g., just an OG image), invoke just that phase

## Hard rules: never break these

These are the rules that made the source build production-grade rather than slop. Violating any of these will get the model in trouble.

1. **NEVER invent facts.** Every claim in metadata, JSON-LD, llms.txt, etc. must trace to existing source content (page text, content/*.ts data files, or user input during the build). If a field is missing, flag it in TODO.md and SKIP the field. Do not write "approximately" or "around 500 students" or "since 1995" unless those are verbatim from a source. The whole AEO premise breaks if AI engines learn untrue facts from your llms.txt.

2. **NEVER change URLs.** Existing URL structure is load-bearing for redirects (e.g., WordPress legacy `/about-us` → `/about` in vercel.json), inbound links, and Google's existing index. Adding metadata doesn't require URL changes; if you find yourself wanting to rename a route, stop and ask.

3. **NEVER add tracking scripts** (Google Analytics, Facebook Pixel, Plausible, etc.) without explicit user approval AND legal review. PDPA (Thailand), GDPR (EU), CCPA (California) all have implications, especially for sites serving minors. The skill assumes a "no tracking" stance as the default.

4. **NEVER skip approval gates** in default mode. The approval gates exist because each phase reveals new judgment calls (which pages to noindex, which fonts to use, which structured-data types to apply). Auto-mode skips the gates but the user must explicitly opt in.

5. **ALWAYS verbatim-match JSON-LD content to rendered content.** Google's Rich Results validator penalizes schema-vs-rendered mismatches. If FAQPage schema says `"Q1 text"` and the rendered HTML says `"Q1 text rephrased"`, Google flags it.

6. **ALWAYS use the source provenance pattern.** For every claim in llms.txt or JSON-LD, document the source line/file in your approval message. This catches inventions before they ship.

7. **ALWAYS build + verify after each phase.** `rm -rf .next out && npm run build` then grep the emitted HTML for the expected output. Skip this and you'll find broken JSON-LD in production via Google Search Console weeks later.

## Phase 1: Per-page metadata

**Goal:** Every user-facing page emits unique `title`, `description`, canonical, hreflang, openGraph, twitter, robots.

**Protocol:**

1. Set `metadataBase` in `src/app/layout.tsx`:
   ```tsx
   export const metadata: Metadata = {
     metadataBase: new URL('https://<DOMAIN>'),
     // ... rest
   };
   ```

2. Survey current per-page metadata. List which pages have `export const metadata` and which don't.

3. **Show draft for 3 sample pages** (homepage + 2 distinct sections) BEFORE applying to all. Pause for approval.

4. After approval, generalize the pattern to remaining pages with a one-table summary of per-page title angles.

**Standard per-page metadata shape:**

```tsx
import type { Metadata } from 'next';

export const metadata: Metadata = {
  title: {
    absolute: '<50-60 char title with brand + primary keyword + location>',
  },
  description:
    '<140-160 char human-readable description with brand mention>',
  alternates: {
    canonical: 'https://<DOMAIN>/<path>/',
    languages: {
      en: 'https://<DOMAIN>/<path>/',
      th: 'https://<DOMAIN>/<path>/',           // if bilingual; same URL OK for CSS-toggle sites
      'x-default': 'https://<DOMAIN>/<path>/',
    },
  },
  openGraph: {
    title: '<same as title>',
    description: '<same or slightly different>',
    url: 'https://<DOMAIN>/<path>/',
    siteName: '<Brand>',
    type: 'website',
    locale: 'en_US',
    alternateLocale: ['<other>_<COUNTRY>'],     // optional
  },
  twitter: {
    card: 'summary_large_image',
    title: '<concise title>',
    description: '<short description>',
  },
  robots: { index: true, follow: true },
};
```

**Key decisions:**

- Use `title.absolute` if the layout has a title template that appends brand chars, gives full SEO control per page.
- For funnel/transitional pages (e.g., a /newsletter that redirects users), set `robots: { index: false, follow: true }`, don't pollute the index with thin content.
- For sites with CSS-only language toggle (one URL serves both languages), hreflang declares every language pointing at the same URL. Suboptimal vs separate `/en/` and `/th/` URL trees but matches the architecture.

**Trailing-slash gotcha:** If `next.config.js` has `trailingSlash: true`, all canonical URLs MUST end with `/`. If `false`, no trailing slash. Mismatch causes "soft canonical" warnings in Google Search Console.

**Verification:**

```bash
rm -rf .next out && npm run build
# Sample emitted HTML
grep -oE '<title>[^<]+</title>' out/about/index.html
grep -oE 'name="description"[^>]+' out/about/index.html
grep -oE 'rel="canonical"[^>]+' out/about/index.html
```

## Phase 2: Site-wide JSON-LD

**Goal:** Every page emits `Organization` (or `EducationalOrganization` / `LocalBusiness` if applicable) + `WebSite` schemas with `@id` cross-references.

**Protocol:**

1. Pull org data from existing content (`content/*.ts`, page content, footer text, contact page).
2. **Show the data dump as a table BEFORE writing the schema.** Approve fields.
3. Add schema constants + an `ldJson()` helper to `src/app/layout.tsx`.
4. Inject as `<script type="application/ld+json">` inside `<head>`.

**Template:**

```tsx
// In src/app/layout.tsx, after `export const metadata = {...}`

const organizationSchema = {
  '@context': 'https://schema.org',
  '@type': 'EducationalOrganization',          // or 'Organization', 'LocalBusiness', etc.
  '@id': 'https://<DOMAIN>/#organization',     // anchor for cross-references
  name: '<Brand>',
  alternateName: '<Native script brand>',     // optional, e.g. Thai/Chinese name
  url: 'https://<DOMAIN>',
  logo: 'https://<DOMAIN>/logo.png',          // must be a real asset; verify it exists
  foundingDate: '<YYYY>',                     // optional
  description: '<institutional 1-2 sentence description>',
  sameAs: [                                   // social profile URLs
    'https://www.facebook.com/...',
    'https://www.instagram.com/...',
  ],
  // For multi-location entities, add subOrganization:
  subOrganization: [
    {
      '@type': 'EducationalOrganization',
      '@id': 'https://<DOMAIN>/<path>/#organization',
      name: '<Location 1 name>',
      url: 'https://<DOMAIN>/<path>/',
      address: {
        '@type': 'PostalAddress',
        streetAddress: '<street>',
        addressLocality: '<city>',
        postalCode: '<zip>',
        addressCountry: '<ISO2>',             // e.g. 'TH', 'US'
      },
      telephone: '+<E.164>',                  // e.g. '+6628099081'
      email: '<contact email>',
    },
    // ... more locations
  ],
};

const websiteSchema = {
  '@context': 'https://schema.org',
  '@type': 'WebSite',
  '@id': 'https://<DOMAIN>/#website',
  url: 'https://<DOMAIN>',
  name: '<Brand>',
  alternateName: '<Native brand>',
  inLanguage: ['en', 'th'],                   // languages the site is available in
  publisher: { '@id': 'https://<DOMAIN>/#organization' },  // CROSS-REFERENCE
};

// Defensive escape: any `<` inside JSON gets encoded so a stray
// `</script>` in future data can't break out of the <script> block.
const ldJson = (obj: unknown) =>
  JSON.stringify(obj, null, 2).replace(/</g, '\\u003c');
```

Then in the `<head>`:

```tsx
<head>
  {/* ... existing head content ... */}
  <script
    type="application/ld+json"
    dangerouslySetInnerHTML={{ __html: ldJson(organizationSchema) }}
  />
  <script
    type="application/ld+json"
    dangerouslySetInnerHTML={{ __html: ldJson(websiteSchema) }}
  />
</head>
```

**Critical patterns:**

- **`@id` cross-references:** Google treats two schemas with the same `@id` as the SAME entity. So a campus that appears in `subOrganization` of the root org AND in `LocalBusiness` on its own page (Phase 3.2) merges into one entity. Use stable URI-style `@id`s: `https://<domain>/#organization` for the root org, `https://<domain>/<path>/#organization` for per-page subOrgs.

- **`publisher.@id` on WebSite:** Tells Google the WebSite and Organization are linked entities. Without this, they look like two separate things.

- **Defensive escape:** The `replace(/</g, '\\u003c')` prevents a hypothetical future data value containing `</script>` from breaking out of the script block. Google's parser decodes `<` transparently. No-op for normal data but cheap insurance.

**Verification:**

```bash
rm -rf .next out && npm run build

# Site-wide emission count (should equal page count)
find out -name "index.html" | xargs grep -l 'EducationalOrganization' | wc -l
find out -name "index.html" | xargs grep -l '"@type": "WebSite"' | wc -l

# Parse JSON-LD on homepage
node -e '
const fs = require("fs");
const html = fs.readFileSync("out/index.html", "utf-8");
const rx = /<script type="application\/ld\+json">([\s\S]*?)<\/script>/g;
let m, i = 0;
while ((m = rx.exec(html))) {
  i++;
  const raw = m[1].replace(/\\u003c/g, "<");
  try {
    const obj = JSON.parse(raw);
    console.log(`Block ${i}: VALID @type=${obj["@type"]} @id=${obj["@id"]}`);
  } catch (e) {
    console.log(`Block ${i}: INVALID, ${e.message}`);
  }
}
'
```

## Phase 3: Per-page JSON-LD

**Goal:** Add page-specific schemas that complement the site-wide ones from Phase 2.

Three sub-phases depending on what pages exist:

### 3.1: FAQPage on `/faq`

For sites with an FAQ page. Extract every Q&A pair verbatim from the rendered accordion content.

**Critical:** FAQPage schema text MUST verbatim-match the rendered text. Google's Rich Results validator penalizes mismatches. If the page has bullet lists in answers, flatten them to plain text for the schema (lose the `<ul>` structure but keep the content).

**Template:**

```tsx
// In src/app/faq/page.tsx, after data definitions

const faqSchema = {
  '@context': 'https://schema.org',
  '@type': 'FAQPage',
  mainEntity: [
    {
      '@type': 'Question',
      name: '<verbatim question text>',
      acceptedAnswer: {
        '@type': 'Answer',
        text: '<verbatim answer text, plain-text flattened>',
      },
    },
    // ... 7 more for an 8-Q FAQ
  ],
};

const ldJson = (obj: unknown) =>
  JSON.stringify(obj, null, 2).replace(/</g, '\\u003c');

export default function FaqPage() {
  return (
    <>
      <script
        type="application/ld+json"
        dangerouslySetInnerHTML={{ __html: ldJson(faqSchema) }}
      />
      {/* ... rest of page ... */}
    </>
  );
}
```

**Apostrophe note:** Most pages use curly apostrophes (`'`, U+2019) for typography. Preserve them in schema text, that's verbatim. JS single-quoted strings handle curly apostrophes natively (they're just text, not delimiters).

### 3.2: LocalBusiness on multi-location pages

For each physical location (campus, office, branch), add a `LocalBusiness` + `EducationalOrganization` combined schema. The `@id` MUST match the `subOrganization` entry's `@id` from Phase 2, that's what makes Google merge the two into one entity.

**Template:**

```tsx
const campusSchema = {
  '@context': 'https://schema.org',
  '@type': ['LocalBusiness', 'EducationalOrganization'],   // array, appears in BOTH verticals
  '@id': 'https://<DOMAIN>/<path>/#organization',          // MATCHES the subOrg @id
  name: '<Location name>',
  url: 'https://<DOMAIN>/<path>/',
  image: 'https://<DOMAIN>/path/to/location-photo.jpg',
  description: '<one-line differentiator from existing content>',
  address: {
    '@type': 'PostalAddress',
    streetAddress: '<street>',
    addressLocality: '<city>',
    postalCode: '<zip>',
    addressCountry: '<ISO2>',
  },
  telephone: '+<E.164>',
  email: '<contact email>',
  parentOrganization: { '@id': 'https://<DOMAIN>/#organization' },  // back-link to root
  // SKIP if not in source data, don't invent:
  // geo: { '@type': 'GeoCoordinates', latitude: ..., longitude: ... }
  // openingHoursSpecification: [...]
};
```

**Skip-with-flag pattern:** If `geo` coordinates aren't in your data files, SKIP the field and add a TODO.md flag. Same for opening hours. Don't invent lat/lng, Google can correlate the address to a location on its own, just slower.

### 3.3: Organization with mainEntityOfPage on /about

A thin schema that re-uses the root Organization `@id` but adds `mainEntityOfPage` pointing at `/about/`. Tells Google "this URL is the canonical description of this entity", boosts Knowledge Panel attribution.

**Template:**

```tsx
const aboutSchema = {
  '@context': 'https://schema.org',
  '@type': 'EducationalOrganization',         // or 'Organization'
  '@id': 'https://<DOMAIN>/#organization',    // SAME as root
  name: '<Brand>',
  url: 'https://<DOMAIN>',
  mainEntityOfPage: {
    '@type': 'WebPage',
    '@id': 'https://<DOMAIN>/about/',
  },
};
```

NO redundant declaration of logo/sameAs/subOrgs here, those are already established by layout.tsx via the shared `@id`. The only NEW signal is `mainEntityOfPage`.

**Verification (all of Phase 3):**

```bash
# /faq should have 3 JSON-LD blocks: Org + WebSite (from layout) + FAQPage (page)
node -e '
const fs = require("fs");
const html = fs.readFileSync("out/faq/index.html", "utf-8");
const rx = /<script type="application\/ld\+json">([\s\S]*?)<\/script>/g;
let i = 0, m;
while ((m = rx.exec(html))) i++;
console.log(`Total JSON-LD blocks on /faq: ${i}`);
'
# Each campus page should also have 3 blocks
```

## Phase 4: AEO files

**Goal:** Three files that make the site machine-readable to AI engines:

### 4.1: `public/llms.txt` (~600 words)

Concise structured knowledge document. Markdown format. AI engines pull this and summarize verbatim, so every sentence must be factually grounded.

**Template:**

```markdown
# <Brand>

> <1-2 sentence overview: what the org is, where, when founded,
> what it offers, who it serves>

## About

<2-3 sentence intro pulled from /about page>

## <Section name: e.g. Campuses, Locations, Products>

### <Item 1 name>
<Tagline>. <Location/key facts>. Contact: <phone>, <email>.

### <Item 2 name>
<...>

## <Programs / Services / Offerings>

<2-3 sentence overview from existing page>

- **<Program 1>**, <one-line description>
- **<Program 2>**, <one-line description>

## Admissions / Contact / How to Get Started

<Brief actionable summary with primary email/phone>

## Key Facts

- Founded: <YYYY>
- Type: <Category>
- <Other factual fields>

## Contact

- Primary email: <email>
- Website: https://<DOMAIN>
```

**Source provenance:** For every claim in the file, document the source line/file in your approval message. The skill's golden rule is "no invention."

### 4.2: `public/llms-full.txt` (~2000-4000 words)

Long-form companion. Pulls full content from /about, /academics (or /products, /services), /faq, /campuses. Strip HTML. Keep prose.

Structure:

```markdown
# <Brand>: Full Knowledge Document

<Same overview block as llms.txt>

## Full History and Mission
<Pulled from /about page, plain text>

## Detailed <Programs/Services/Products>
<Pulled from /academics or /products page, plain text>

## Frequently Asked Questions

### Q: <question 1>
<answer 1>

### Q: <question 2>
<answer 2>

## <Location/Branch> Details

### <Location 1>
<Full page content for that location>

## How to Engage / Apply / Buy
<Pulled from /admissions or /contact page>
```

Bilingual content: include English only. AI engines infer cultural context from English mentions; duplicating bilingual content bloats the file.

### 4.3: `public/robots.txt` with AI crawler allowlist

If using `next-sitemap`, generate via the config (one source of truth). Otherwise edit `public/robots.txt` directly.

**Via `next-sitemap.config.js`:**

```js

  policies: [
    { userAgent: 'GPTBot', allow: '/' },
    { userAgent: 'ClaudeBot', allow: '/' },
    { userAgent: 'anthropic-ai', allow: '/' },
    { userAgent: 'Google-Extended', allow: '/' },
    { userAgent: 'PerplexityBot', allow: '/' },
    { userAgent: 'Applebot-Extended', allow: '/' },
    { userAgent: 'CCBot', allow: '/' },
    { userAgent: 'Bytespider', allow: '/' },
    { userAgent: 'Amazonbot', allow: '/' },
    { userAgent: '*', allow: '/' },
  ],
},
```

**Static `public/robots.txt`:**

```

Allow: /

User-agent: ClaudeBot
Allow: /

User-agent: anthropic-ai
Allow: /
```

**Why each bot matters:**

- **GPTBot**, OpenAI's web crawler that feeds ChatGPT.
- **ClaudeBot / anthropic-ai**, Anthropic crawlers for Claude.
- **Google-Extended**, Google's Bard/Gemini training crawler (distinct from regular Googlebot).
- **PerplexityBot**, Perplexity's live search crawler.
- **Applebot-Extended**, Apple Intelligence training.
- **CCBot**, Common Crawl, feeds many AI models including Anthropic and OpenAI training data.
- **Bytespider**, ByteDance (TikTok / Doubao search).
- **Amazonbot**, Amazon's emerging search products.

These crawlers default to disallow on many sites that haven't explicitly allowed them. Explicit allowlist signals "we want to be discoverable to AI search."

## Phase 5: Image SEO + dynamic OG image

### 5.1: Image alt text audit

Audit every `<Image>` (next/image) and `<img>` in `src/`. For each:

- Is it **decorative** (purely visual, no info) → `alt=""` is correct
- Is it **content** (conveys info) → `alt="<descriptive>"` required
- Is it **brand/logo** → `alt="<Brand name>"`

Common patterns:

| Image type | Recommended alt |
|---|---|
| Hero photo collage (decorative) | `alt=""` |
| Logo | `alt="<Brand>"` |
| Author/testimonial avatar | `alt="<author name>"` |
| Card photo with title visible elsewhere | `alt="<descriptive>"` (don't repeat the title) |
| Gallery thumbnail in linked card | `alt=""` if card link has aria-label |
| Lightbox/modal full image | `alt="<descriptive>"` |

**WP-imported HTML alt cleanup** (if migrating from WordPress): WP-imported `<img>` tags often have Facebook photo IDs or filename junk in alt attributes (`alt="105491093_3643628198..."`). Screen readers read these aloud, worse than empty. Bulk-replace with `alt=""` for decorative or descriptive text for content.

### 5.2: Dynamic OG image at `src/app/opengraph-image.tsx`

1200×630 brand-aware PNG generated at build time. Next.js auto-attaches to `og:image` and `twitter:image` meta tags.

**Critical for `output: 'export'`:** The default `runtime: 'edge'` makes the route DYNAMIC (`ƒ` in build manifest), which static export refuses to emit. Forcing `runtime: 'nodejs'` + `export const dynamic = 'force-static'` makes it Static (`○`) and emits a PNG to `out/opengraph-image`.

**Template:**

```tsx
import { ImageResponse } from 'next/og';

export const runtime = 'nodejs';
export const dynamic = 'force-static';
export const alt = '<Brand> · <Tagline>';
export const size = { width: 1200, height: 630 };
export const contentType = 'image/png';

// Load Google Font as TTF. Satori requires TTF/OTF, woff2 NOT supported.
// Old User-Agent forces Google Fonts API to return TTF instead of woff2.
async function loadGoogleFont(
  family: string,
  weight: number,
  text: string,
): Promise<ArrayBuffer> {
  const familyParam = encodeURIComponent(family);
  const url =
    `https://fonts.googleapis.com/css2?family=${familyParam}:wght@${weight}` +
    `&text=${encodeURIComponent(text)}`;
  const css = await fetch(url, {
    headers: { 'User-Agent': 'curl/7.79.1' },
  }).then((r) => r.text());
  const match = css.match(/src: url\(([^)]+)\) format\(['"]truetype['"]\)/);
  if (!match) {
    throw new Error(`opengraph-image: no TTF URL for ${family}:${weight}`);
  }
  return fetch(match[1]).then((r) => r.arrayBuffer());
}

// Pull brand colors from tailwind.config (don't hardcode if you can avoid it).
const BRAND_PRIMARY = '<hex from tailwind.config>';     // e.g. '#1c4f26'
const BRAND_ACCENT = '<hex>';                            // e.g. '#d4a94a'
const BRAND_PAPER = '#fefefe';
```

### 5.3: `vercel.json` Content-Type header (CRITICAL)

The OG image is emitted as `out/opengraph-image` (NO `.png` extension). Vercel serves extensionless files as `application/octet-stream` by default, which breaks OG crawlers. Add a header rule:

```json
{
  "headers": [
    {
      "source": "/opengraph-image",
      "headers": [
        { "key": "Content-Type", "value": "image/png" },
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    },
    {
      "source": "/opengraph-image/",
      "headers": [
        { "key": "Content-Type", "value": "image/png" },
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    }
  ]
}
```

**TWO RULES REQUIRED**, one for no-trailing-slash, one for trailing-slash. With `trailingSlash: true` Next.js serves the image at `/opengraph-image/`. Without both rules, the Content-Type only applies to one variant. Vercel's path-to-regexp doesn't honor `{/,}` optional-group syntax, must be explicit.

The 1-year immutable cache is safe because Next.js appends a content-hash query string (`?abc123`) to the OG image URL in meta tags. When the image content changes, the hash changes, the URL changes, the cache busts automatically.

**Verification after deploy:**

```bash
curl -sI https://<DOMAIN>/opengraph-image/ | grep -i content-type
# Expected: content-type: image/png

# Magic byte sanity
curl -s https://<DOMAIN>/opengraph-image/ -o /tmp/og.png && file /tmp/og.png
# Expected: PNG image data, 1200 x 630
```

## Phase 6: Sitemap tuning

**Goal:** Sitemap contains only indexable URLs, with sensible priority/changefreq.

**Standard `next-sitemap.config.js`:**

```js
/** @type {import('next-sitemap').IConfig} */
module.exports = {
  siteUrl: process.env.SITE_URL || 'https://<DOMAIN>',
  generateRobotsTxt: true,
  outDir: 'out',
  trailingSlash: true,

  transform: async (config, path) => {
    // Normalize trailing slash for lookups
    const cleanPath = path.replace(/\/$/, '') || '/';

    // Exclude noindex pages + error routes + non-HTML routes
    if (
      [
        '/newsletter',         // noindex funnel page
        '/school-calendar',    // noindex funnel page
        '/_not-found',         // 404
        '/404',                // 404
        '/opengraph-image',    // it's a PNG, not HTML
      ].includes(cleanPath)
    ) {
      return null;
    }

    // Per-route priority + changefreq
    const map = {
      '/':              { priority: 1.0, changefreq: 'weekly'  },
      '/about':         { priority: 0.9, changefreq: 'monthly' },
      '/products':      { priority: 0.9, changefreq: 'monthly' },
      '/services':      { priority: 0.9, changefreq: 'monthly' },
      '/contact':       { priority: 0.7, changefreq: 'yearly'  },
      '/faq':           { priority: 0.7, changefreq: 'monthly' },
      // ... your routes
    };
    const settings = map[cleanPath] || { priority: 0.7, changefreq: 'monthly' };

    return {
      loc: path,
      changefreq: settings.changefreq,
      priority: settings.priority,
      lastmod: new Date().toISOString(),
      alternateRefs: config.alternateRefs ?? [],
    };
  },

  robotsTxtOptions: {
    policies: [
      // ... AI crawler allowlist from Phase 4.3
    ],
  },
};
```

**Priority/changefreq guidelines (Google treats these as weak signals, still helpful for crawl budget):**

| Route type | Priority | Changefreq |
|---|---|---|
| Homepage | 1.0 | weekly |
| Top-level content pages | 0.9 | monthly |
| Sub-pages (campus, product, location detail) | 0.8 | monthly |
| Contact | 0.7 | yearly |
| FAQ | 0.7 | monthly |
| News/blog index | 0.5-0.7 | weekly or daily |
| Careers | 0.5 | monthly |
| Testimonials | 0.5 | monthly |

**Verification:**

```bash

curl -s https://<DOMAIN>/sitemap-0.xml | python3 -c '

for url in re.findall(r"<url>(.*?)</url>", xml):
  loc = re.search(r"<loc>(.*?)</loc>", url).group(1)
```

## Pitfalls library: things that will bite you

Real bugs from real production builds. Worth memorizing.

### Vercel + `trailingSlash: true` breaks single header rules

**Symptom:** Your `vercel.json` header rule on `/opengraph-image` doesn't apply. Production serves `application/octet-stream`.

**Cause:** With `trailingSlash: true`, Next.js serves the image at `/opengraph-image/` (with slash). Vercel's `source` match is literal, `/opengraph-image` ≠ `/opengraph-image/`.

**Fix:** Use TWO explicit header rules, one for each variant. The `{/,}` optional-group syntax does NOT work in Vercel's path-to-regexp version. Don't trust it.

### `next/og` + `output: 'export'` makes the OG route dynamic

**Symptom:** Build manifest shows `ƒ /opengraph-image` (Dynamic) instead of `○` (Static). No PNG is emitted to `out/`. Production has no OG image.

**Cause:** Default `runtime: 'edge'` for opengraph-image makes the route dynamic, which static export can't materialize.

**Fix:** Set `runtime: 'nodejs'` AND `export const dynamic = 'force-static'`. Both required.

### Vercel bot mitigation challenges your verification IP

**Symptom:** After pushing and polling production, every URL returns HTTP 403 with `x-vercel-mitigated: challenge`. You can't verify anything from your machine.

**Cause:** Aggressive polling (e.g., 36 requests in 3 min) trips Vercel's bot protection. It locks your IP for ~15-30 min.

**Fix:** Pace production health checks at ≥60s intervals. If already tripped, stop hammering and ask the user to verify from their browser. The challenge self-clears after the cool-down.

### Google Fonts CSS returns woff2; Satori requires TTF

**Symptom:** `opengraph-image.tsx` build fails with "No TTF found in CSS for <font>".

**Cause:** Modern User-Agents get woff2 from Google Fonts. Satori (next/og's renderer) doesn't support woff2.

**Fix:** Pass an old User-Agent so Google Fonts returns TTF format:
```ts
fetch(url, { headers: { 'User-Agent': 'curl/7.79.1' } })
```

### Title template eats SEO budget

**Symptom:** Per-page titles get truncated in Google because the layout template appended ` | <Brand>` is taking 20+ chars.

**Cause:** `title.template` in layout always appends. Per-page `title: 'X'` becomes `'X | <Brand>'`.

**Fix:** Use `title.absolute` per page to bypass the template:
```tsx
title: { absolute: 'Full 50-60 char title' }
```

### FAQ schema mismatch fails Rich Results validator

**Symptom:** Google Search Console flags "Content doesn't match" for FAQPage.

**Cause:** Schema text differs from rendered text, even small differences (curly vs straight apostrophe, missing punctuation, paraphrased).

**Fix:** Verbatim-match. If the rendered answer has bullet lists, flatten to plain text for the schema but keep all the actual words.

### WP-imported HTML has Facebook photo IDs in alt text

**Symptom:** Screen readers say "one zero five four nine one zero nine three underscore three six four three..."

**Cause:** WordPress media library populated alt text from Facebook export filenames. WP HTML imports preserved them.

**Fix:** Bulk-replace via regex sweep through the HTML content file. Pattern: `alt="[A-Za-z0-9_-]{15,}"` → `alt=""`. Decorative imgs lose nothing; content imgs need real alt text added separately.

### Noindex page in sitemap = "Submitted URL marked noindex" warning

**Symptom:** Search Console keeps showing the same warnings every week.

**Cause:** Page has `robots: { index: false }` in metadata AND is in the sitemap. Conflicting signals.

**Fix:** Exclude noindex pages from the sitemap (`return null` in next-sitemap's `transform`).

### `runtime: 'edge'` + Google Fonts CSS fetch may fail at build

**Symptom:** Random build failures when fetching Google Fonts.

**Cause:** Edge runtime has stricter fetch limits than Node.

**Fix:** Use `runtime: 'nodejs'` for OG image generation (also required for static export, see above).

## Adapt to other frameworks

This skill assumes Next.js 14+ App Router with `output: 'export'` on Vercel. Adaptations:

### Next.js Pages Router

- Metadata via `next/head` instead of `export const metadata`.
- No `app/opengraph-image.tsx`, use `next-og-image` or a script that generates a static PNG at build time.

### Next.js SSR (no `output: 'export'`)

- OG image can use `runtime: 'edge'`, works at request time.
- Sitemap can use `getStaticPaths` to enumerate dynamic routes.

### Other static-site generators (Astro, Eleventy, Hugo)

- Phase 1 (metadata): use the framework's head templating.
- Phase 2-3 (JSON-LD): inject in head template, same templates.
- Phase 4 (AEO files): just static files in the output directory. Same content.
- Phase 5 (OG image): use a build-time image generation tool (`@vercel/og` standalone, or Satori directly).
- Phase 6 (sitemap): framework-specific sitemap plugin.

### WordPress / CMS-rendered sites

- This skill is the wrong shape, WP has Yoast or RankMath plugins that cover SEO. AEO files would be uploaded manually to the WP file manager.
